# 谛听云社区版 · 架构设计

## 设计原则

1. **5 分钟跑起来** — `docker compose up -d` 是唯一需要的命令
2. **零外部服务依赖** — 不要求 MySQL / Redis / MQ / 向量数据库，单容器自足
3. **数据完全私有** — 所有音视频与转写数据存储在本地卷，不上传任何遥测
4. **代码可读性优先** — 开源的信任来自"任何人都能读懂"，拒绝过度抽象

## 技术选型

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 后端 | Go 单二进制 | 编译产物即交付物，自托管体验最好；与团队既有技术栈一致 |
| 存储 | SQLite（内嵌） | 单机场景零运维；元数据 + 向量索引一体 |
| ASR 转写 | OpenAI 兼容 Whisper API（可插拔） | 屏蔽供应商差异，Deepgram/阿里云/自建 whisper.cpp 皆可接入 |
| 清洗纠错 | OpenAI 兼容 LLM（可插拔） | 语气词过滤 + 术语修正，模型可自由替换 |
| 前端 | 服务端直出（MVP）→ 独立 Web UI | MVP 阶段先让管道跑通，再投入交互体验 |
| 部署 | Docker Compose 单服务 | 一条命令，一份数据卷 |

**刻意不做的**：不内嵌模型权重下载、不强依赖 GPU、不引入消息队列。这些属于云端版的规模化工件，对单机自托管是负担。

## 数据流

```
上传 → 抽音频(ffmpeg) → Whisper 转写 → LLM 清洗纠错
     → 切片(chunking) → Embedding 向量化 → SQLite 落库
     → 语义检索 / RAG 问答（答案引用时间戳）
```

## 开源边界（Open-Core 划分）

谛听云采用 Open-Core 模式。以下能力**仅存在于商业云端版**，不会进入本仓库：

| 闭源能力 | 不开源的原因 |
| --- | --- |
| 术语纠错优化 | 云端积累的领域术语体系，社区版提供基础 LLM 纠错 |
| 多租户 / RBAC / 配额计费 | 云端运营工件，单机场景无意义 |
| 支付 / 微信生态 / 邀请裂变 | 商业闭环，与开源用户无关 |
| Milvus 分布式向量集群 | 云端规模化基础设施，单机用 SQLite 更优 |
| 审计日志 / SLA / 私有化交付工具链 | 企业合规交付物 |

划分原则：**社区版完整覆盖"个人与小团队的私有知识库"场景；当团队长大、需要协同与合规时，自然演进到云端版。**

## 目录结构（规划）

```
ditingyun/
├── cmd/ditingyun/      # 程序入口
├── internal/
│   ├── config/         # 环境变量配置
│   ├── ingest/         # 上传与音频抽取
│   ├── transcribe/     # Whisper 转写（可插拔）
│   ├── polish/         # LLM 清洗纠错（可插拔）
│   ├── index/          # 切片与向量化
│   ├── retrieve/       # 语义检索与问答
│   └── store/          # SQLite 持久层
├── assets/             # 品牌资产
├── docs/               # 文档
├── Dockerfile
└── docker-compose.yml
```

## 与云端版的关系

- 本仓库（`DiTingAI/ditingyun`）：社区版核心引擎，AGPL-3.0
- 官网（[ditingyun.cn](https://ditingyun.cn)）：云端托管版入口，私有仓库独立迭代
- 两者共享品牌与产品理念，代码边界清晰、互不依赖
